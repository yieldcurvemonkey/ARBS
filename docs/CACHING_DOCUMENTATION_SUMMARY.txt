KEY FINDINGS
================================================================================

DETERMINISM
-----------
The caching system ensures determinism through:
  • Deterministic key generation (JSON with sort_keys=True)
  • Content-addressed Parquet storage (SHA256 hashing)
  • ACID transactions with all-or-nothing semantics
  • Immutable storage once committed

PERFORMANCE
-----------
Optimized for efficiency through:
  • OOBTree O(log n) access for large datasets
  • Connection pooling (reuse vs create)
  • Batched writes (1 fsync for 10,000 items)
  • Lazy loading (only needed pages in memory)
  • Compression support (80-90% reduction)

THREAD SAFETY
-----------
Protected through 3-level locking:
  • Registry lock: Database creation
  • Connection pool lock: Connection reuse
  • Transaction manager: Per-thread isolation

SCALABILITY
-----------
Handles massive datasets:
  • 100M+ items per cache file (OOBTree)
  • 256 shards for distribution
  • Unlimited concurrent readers
  • Single writer per file

================================================================================
CRITICAL DESIGN DECISIONS EXPLAINED
================================================================================

1. Reference Counting (_DBHandle)
   Why: Proper resource cleanup without explicit management
   How: Track refcnt, close only when refcnt == 0
   Benefit: Multiple instances can share same database file

2. OOBTree vs PersistentMapping
   Why: Performance scales with dataset size
   When: Use OOBTree for >10K items, PersistentMapping for small caches
   Result: 100x memory reduction for large caches

3. FileStorage Backend
   Why: Durability and ACID guarantees
   How: Transaction-based writes with fsync
   Benefit: Data survives crashes, all-or-nothing commits

4. Sharding Strategy
   Why: Distribute load and reduce tree depth
   How: SHA256 hash first 2 chars (256 buckets)
   Result: Faster lookups even with millions of symbols

5. CodecMapping Wrapper
   Why: Transparent serialization without code changes
   How: Wraps backing store, encode on write, decode on read
   Benefit: Can swap encoders (JSON, zlib, pickle, etc.)

USAGE RECOMMENDATIONS
================================================================================

WHEN TO USE THIS CACHE:
  ✓ Caching expensive computations
  ✓ Storing time-series data
  ✓ Building reproducible analytics
  ✓ Sharing data between processes
  ✓ Persisting model results

WHEN NOT TO USE:
  ✗ High-frequency trading (too much latency)
  ✗ Real-time applications
  ✗ Simple in-memory caching (use Redis)
  ✗ Distributed caches (single machine only)

CONFIGURATION GUIDELINES:
  • Use use_btree=True (default) for production
  • Batch writes with .batched() context manager
  • Commit after each operation for safety (or batch)
  • Always call close_zodb() for cleanup
  • Use CodecMapping for large objects
  • Monitor with diagnostics() to detect leaks
